# 历史补采 DNS 故障复盘（2026-09-08）

## 结论

初始化活动 #66 并不是“仍在慢慢采集”，而是在核心历史阶段被一次共享 DNS
故障阻断。2026-09-08 00:07–00:11（Asia/Shanghai），`worker-backfill` 无法解析
`api.waditu.com`，177 个日期任务在过短的 10/20 秒重试窗口内耗尽 3 次尝试：

| 接口 | 最终失败任务数 |
|---|---:|
| `daily` | 36 |
| `daily_basic` | 36 |
| `index_daily` | 36 |
| `stk_limit` | 35 |
| `moneyflow` | 34 |

其中 175 个失败日期没有数据，另外 2 个 `index_daily` 日期已存在旧数据。更重要的
影响是状态机进入 `attention` 后停止生成后续历史任务，因此当时还有约 1.77 万个
核心历史步骤尚未完成。最近 120 天覆盖审计仍为完整，只能证明当前窗口连续，不能
证明全历史初始化已完成。

## 为什么此前没有及时发现

1. 单任务有重试，但没有共享网络故障的资源池退避。每个任务都在几十秒内独立耗尽
   重试，批量故障被放大。
2. 初始化进入 `attention` 后只能人工恢复，没有利用任务中已经保存的
   `failure.category=network` 与 `retryable=true` 做安全自愈。
3. 早期专项任务没有持久化规范 `api_name`。控制台按接口聚合时只识别
   `api_name`/通用任务参数，导致 `daily`、`daily_basic`、`moneyflow`、`stk_limit`
   的失败没有进入接口级失败列表。
4. 控制台的覆盖审计默认观察最近 120 天，而初始化进度代表全历史传输任务；两个
   口径没有相互替代关系。页面虽然已有初始化状态，但接口失败漏报削弱了阻断信号。
5. 数据规模使用 `pg_stat_user_tables.n_live_tup` 单一估计。大量 UPSERT 或统计重置
   后它可能为 0 或远低于实际值；规范化当前视图还没有自己的表行数统计。

## 已实施的治理

- 网络/DNS 故障按 60、300、900 秒退避，并同步推迟相同 `resource_class` 的全部
  待执行叶子任务，避免共享事故批量消耗重试。
- 初始化只对当前阶段全部明确属于 `network`、`timeout`、`quota` 且
  `retryable=true` 的最终失败自动恢复；完整性、权限、参数、处理器和覆盖错误继续
  停在 `attention`。自动恢复默认冷却 300 秒、最多 3 轮，并使用独立持久化计数，
  不再误用人工 `verification_round`。
- 所有专项任务在创建时写入规范 Tushare API 名；迁移 043 回填历史任务，使旧失败
  能被接口级监控识别，并能由同接口同周期的后续成功准确消除。
- 旧任务即使没有可关联的后续采集任务，只要该接口对应数据集在失败之后完成了覆盖
  该日期的严格 `complete` 审计，也视为已经恢复；这消除了“表中已有 7,768 行且
  最新 120 天审计完整，但 2026-08-31 `stk_limit` 仍显示失败”的假告警。
- 数据行数估计取 `n_live_tup` 与 `pg_class.reltuples` 的较大值；如果数据集读取
  PostgreSQL 视图，则通过系统依赖关系追踪到底层表统计。
- `moneyflow(trade_date)` 增加索引，日期分区查询从全表并行扫描变为索引扫描。
- 已有业务表但缺少持久任务谱系的共享普通/VIP 接口不再显示为“从未采集”，改为
  信息级 `collection_lineage_missing`，与真实空表分开。

## 验证证据

- 单元测试：274 项通过。
- PostgreSQL 契约测试：36 项通过、1 项因活动初始化存在按设计跳过；新增的资源池
  退避和视图行数估算测试均通过。
- 迁移 043 已在真实 PostgreSQL 应用；13,858 条历史专项任务获得规范接口标识。
- `moneyflow` 单日计数计划已使用 `idx_moneyflow_trade_date` 的 Index Only Scan。
- API 真实返回的估算行数恢复到合理数量级：`daily` 约 593 万、`daily_basic`
  约 564 万、`index_daily` 约 603 万、`moneyflow` 约 205 万。
- 部署后 #66 自动从 `attention` 恢复到 `running`，旧失败步骤被重新生成；首轮观察
  新任务连续成功且没有新增失败。

## 当前边界

本次修复证明补采能够继续，并不表示全历史已经完成。只有 #66 依次完成核心历史、
财务历史、目录历史、最新基线、全量扇出和最终覆盖验收，并进入 `completed`，系统才
会报告全历史完成。Dashboard 和 `GET /api/v1/data-health` 必须继续以初始化状态为
准，不得用最近 120 天 `missing_partitions=0` 替代全历史结论。
