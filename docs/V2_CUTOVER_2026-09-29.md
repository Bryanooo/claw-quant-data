# V2 切换与运维

## 切换结论

自 2026-09-29 起，Tushare 日常采集、历史修复、初始化、验证、Dashboard 和测试只使用 V2。V1 Python 运行包、API、容器、测试以及 `sys_collection_*` / `sys_collector_run` 控制表均已移除。

业务数据表没有因切换而重建。V2 继续写入原有精确业务表，因此不存在 V1/V2 双写，也不需要保留一份 V1 业务数据副本。

## 上线检查

```bash
docker compose ps
curl -fsS http://127.0.0.1:8000/api/v1/ops/orchestration-v2/summary
curl -fsS http://127.0.0.1:8000/api/v1/ops/data-health
curl -fsS http://127.0.0.1:8000/api/v1/data/sources
```

控制面应只有五张表：

```sql
\dt orchestration_v2.*
```

容器应只有 `api`、`scheduler`、`auditor`、`worker-v2-routine`、`worker-v2-backfill`、`postgres`、`backup` 和一次性 `migrate`。

## 定义发布

代码中的 endpoint、任务或审计契约变更后执行：

```bash
docker compose run --rm --no-deps api \
  python scripts/bootstrap_orchestration_v2.py --apply-drafts --publish-ready
```

发布会保留旧版本为 `retired`。已冻结到旧版本的异常实例不能静默改义，应显式 supersede 后创建替代实例。

## 初始化和修复

初始化 API 先扫描全部数据集，再只为当前规则确认的问题创建 V2 repair 实例。历史 Worker 在交易日 08:30–16:00 暂停领取新实例。例行 Worker 独立运行，不被历史队列占用。

全盘审计后可先只读查看计划，再幂等创建缺口实例：

```bash
docker compose run --rm --no-deps api python -m scripts.queue_v2_repairs
docker compose run --rm --no-deps api python -m scripts.queue_v2_repairs --apply
```

该命令按“任务 × 逻辑周期”去重；重复执行只返回既有实例，不会重复采集。

运维时必须同时检查：

- execution 的 queued/running/retrying/attention；
- dataset state 的 gaps/partial/indeterminate；
- 当前规则版本的 coverage audit；
- worker、scheduler、auditor 心跳；
- 上游 quota、permission、network 和 completeness 分类。

“今日运营”只选择 `purpose=daily` 且 `trigger_source=schedule` 的例行实例。
初始化、手工补采和 repair 实例即使与例行实例的数据日期相同，也不能覆盖
今日视图；它们在执行实例和修复视图中单独展示。`ccass_hold`、
`etf_share_size`、`margin`、`margin_detail` 是次晨发布任务，在下一发布窗口
之前显示为 `not_due`，不能误报为“未派发”。

一个 V2 实例始终对应一个业务逻辑周期。分页、交易所和实体范围都在 acquire
节点内部完成并保存请求级证据，不拆成调度层子任务。已经实测支持完整市场级
分页的 `fund_nav`、`fund_portfolio`、`index_weekly`、`index_monthly` 不得退回
旧的逐实体 fan-out；重试必须从 `task_execution_event` 的全部请求证据恢复，
不能受 Dashboard 分页上限影响。

### 2026-09-29 全量复审基线

切换时使用 V2 初始化链路对 194 个可审计数据集执行了全范围审计、
缺口修复和修复后复审。最终初始化状态为 `ready`，最终一轮 194/194
审计成功，835 个初始化修复/核验实例成功，当前规则确认缺失分区为 0。
逐数据集证据见
[`reports/dataset_audit_latest.md`](../reports/dataset_audit_latest.md)。

这里的 `ready` 表示“已确认缺口均已处理”，不表示可以虚构稀疏事件型
接口的历史发布日历。报告中的 `unverified` 仍然保持 fail-closed：它包括
上游没有可靠历史起点、只能按已声明采集范围验证，或需要显式实体范围的
数据集；不能把这些状态展示为“历史完整”。

V2 对上游权威零行使用 `empty_verified`。日分区使用当日，月/季度分区使用
逻辑周期末日作为证书键；迁移 079 仅将同时具有零行采集事件、完整性证明且
没有任何非零行事件的早期 V2 状态归一化，业务数据表不被改写。

### 切换后日常验收口径

任务 `success` 只表示工作流走完；Dashboard 的“严格就绪”还要求该实例发布了
至少一个 dataset state、全部 state 为 ready 且没有 gaps/partial/indeterminate。
若精确日期重采后实体覆盖仍不足，实例必须保留为 `attention/data_incomplete`，
不能降低阈值或把任务成功当成数据完整。

2026-09-29 与 2026-09-30 的 `index_daily` 首次采集分别只有 8,276 行，
其中 CNI 子市场只有 2 行，而 2026-09-28 有 948 行。精确单指数探测证明数据
并非不可获取；23:50 后重新分页可取得 10,457/9,241 行，其中 CNI 为
1,116/949 行。V2 已通过新的 `repair` 实例重新执行 acquire、validate、publish，
两个日期均恢复为 `complete/ready`。原 daily 实例仍保留 attention 作为审计
历史，今日交付视图按最新 dataset state 显示 `ready_after_repair`，不会再用旧
失败实例覆盖已修复的数据状态。调度器新增 23:58 晚发布数据自动补采，用新
repair 实例重新采集，而不是从旧实例的 publish 节点空转重试。

2026-09-30 的接口级落地复查为：201 个可采集接口全部有实现，当前 V2 实际
自动调度 150 个选中端点，197 个接口已有正行数业务数据。剩余 4 个中，
`p_list` 已执行并以 `empty_verified` 严格证明当期为空；`ccass_hold_detail`、
`p_get`、`stk_mins` 分别要求机构/组合/证券分钟范围，均为 disabled/manual，
没有可安全推断的“全市场全部历史”范围，因此保持无数据和手工范围要求，不能
为了凑数发起无界补采。逐接口证据见
[`reports/tushare_data_presence_latest.md`](../reports/tushare_data_presence_latest.md)。

## 备份

```bash
./scripts/backup.sh
./scripts/restore.sh backups/claw-quant-YYYYMMDD-HHMMSS.dump \
  --database claw_quant_restore_drill --yes
```

备份脚本在原子改名之前执行 `pg_restore --list`，并生成 `.sha256`。恢复脚本先校验哈希与目录，再恢复并确认 V2 五张表。`tushare_raw_record` 只保留表结构；它是可重建的异常载荷缓存。业务表、审计证据、迁移账本和请求级证据都会备份。

发布新备份前必须恢复到临时库，并核对 V2 表数、V1 表数、最新迁移以及核心业务表行数。不能只以 `pg_dump` 退出码判断备份可恢复。

恢复演练结束后可显式删除临时数据库：

```bash
docker compose exec -T postgres sh -c \
  'dropdb -U "$POSTGRES_USER" --if-exists claw_quant_restore_drill'
```

恢复验收必须命中当前最新迁移（现为
`079_normalize_v2_verified_empty_states`），不能只检查较旧迁移仍然存在。

2026-09-30 已对 `claw-quant-20260930-143641.dump` 完成 SHA-256、归档目录和
隔离数据库全量恢复演练；恢复库约 149GB，并在恢复库上通过 8 项 PostgreSQL
集成契约测试。演练库、旧 2026-09-29 备份和失败 `.partial` 随后均已删除，
当前仅保留这份已验证备份及其校验文件。

## 外部金融数据源

`financial_data` 是 query-through connector，不落入 Tushare 定时采集队列。
入口为 `POST /api/v1/data/sources/financial_data/query`，只允许审计清单中的
163 条业务路由，并统一执行超时、协议校验和熔断；绝不接受任意 URL。

部署前必须在 `.env` 设置 `FINANCIAL_DATA_API_KEY` 并重建/重启 API。密钥为空
时接口按配置错误失败，不能把本地协议测试当成真实上游已连通。

Connector 统一的是执行信封，不是供应商原始字段。Financial Data 的
`common_query` 仍返回其原生协议；Tushare 定时采集则落到业务表。Agent 只能
依赖数据集层或 `/api/v1/research/*` 的规范模型。只有完成字段、标的代码、单位、
复权与时间语义映射并通过同一审计契约的路由，才允许登记为同一规范数据集的
备用来源；不能因为两个源都提供“日 K”就认为可以任意互换。

## 回滚边界

V1 已删除，不能通过重新启动旧容器回滚。代码回滚必须仍能读取当前业务表和迁移账本；数据库恢复只使用经过演练的 custom-format 备份。任何回滚都不得删除 `orchestration_v2.task_execution_event` 的历史证据。
