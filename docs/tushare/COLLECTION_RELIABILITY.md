# Tushare 采集完整性与可靠性策略

更新日期：2026-09-08。接口事实与权限以 [全接口目录](README.md) 和
[机器可读契约](contracts.json) 为准；本文描述运行时如何保证数据不会因
分页、限流、进程重启或错误重试而被静默截断。

## 当前自动编排覆盖

机器契约承载多个 API，普通/VIP 接口也可能共享一个专项采集器。

| 编排方式 | 接口数 | 落库方式 |
|---|---:|---|

| 周期全量扇出 | 19 | 冻结依赖宇宙，跨有界父子批次自动续跑 |

暂不自动运行不是权限或实现缺失，而是系统尚不能证明自动请求完整、安全：

| 原因 | 数量 | 接口 |
|---|---:|---|
| 初始化基线有覆盖、暂不做周期高基数扇出 | 10 | 筹码、股东、财务审计、指数权重等 |
| 单日全市场规模不可控 | 1 | `ccass_hold_detail` 单日超过百万行，必须明确股票或日期范围 |
| 必填枚举或业务范围需人工指定 | 2 | `fund_basic` 由初始化按 E/O 范围采集；`fut_weekly_detail` 需显式品种范围 |
| 极低频率限制 | 1 | `stk_mins` 保持按需，避免小时级配额被无界标的扇出耗尽 |
| 依赖调用方名称清单 | 1 | `p_get` 只允许显式依赖清单 |
| 实时按需查询 | 1 | `rt_hk_k` 必须显式给出港股代码或官方通配符，不进入历史回填 |

这 16 个接口仍有通用或专项采集实现，但不会用猜测参数自动调用。当前已为 36 个
契约明确的代码/枚举扇出接口建立白名单规划；接口清单可由
`GET /api/v1/collection-batches/fanout-definitions` 查询。低频权限、二维因子参数、
缺失依赖清单或契约不足的接口仍不会进入批量队列。

### 覆盖规则版本化与无损重审

覆盖规则带有显式 `revision`。当参考宇宙、发布时间或完整性阈值经官方契约和真实
数据验证后发生变化，Scheduler 会自动找出旧版本产生的 `gaps` 审计。只有采集任务
本身已经具备 `verified=true` 的分页/范围耗尽证据时，系统才把关联 Auditor 任务原地
重排队；这个过程不调用 Tushare、不重写业务数据，并在同一事务中把采集任务切换为
`verifying`，避免控制台继续展示过期结论。

2026-09-08 的 `index_daily` 复核确认两项契约边界：官方接口明确不包含申万指数，
因此参考宇宙排除 `market=SW`，申万日线由 `sw_daily` 独立负责；CSI/CNI 中的海外及
跨市场指数在部分 SSE 开市日会因当地休市不发布，相邻日真实截面验证的最低正常比例
约为 87%，故告警阈值设为 85%。该阈值仍会拒绝 8,000 行上游截断或丢失一个 5,000
行分页的结果。

`index_basic` 没有完整的历史退市/失效字段，因此不能把今天的指数清单当作三十年前
的精确截面。与初始化契约一致，`index_daily` 只在最近 120 天启用当前参考宇宙的
严格截面阈值；更早的逐日历史仍必须具备成功、分页耗尽和日期回显证据，并检查日期
分区存在，但不会因今天的指数清单变化被反向判错。

财务报表存在同类但更明显的历史口径差异：`stock_basic` 的上市日期不能还原 Tushare
在三十年前实际保留的报表公司宇宙，且后来上市公司可能补录更早报告期。利润表、
资产负债表、现金流量表和财务指标只在最近五年使用当期上市公司比例校验；更早报告期
仍必须满足 offset 分页穷尽、报告期回显，并证明分区存在或该精确报告期为严格验证空。
近五年的空结果仍判为不完整。规则修订后由版本化重审恢复旧的假 `partial`，不会重新
请求上游，也不会绕过分页截断保护。

周线、月线及日更周/月线任务按 `trade_date + freq + source` 精确核对落库行数，并把
官方单次 6,000 行上限作为失败关闭边界；旧的正行数任务可由专项完成证据对账器
无上游请求地升级。控制台还会按 `schedule_id` 关联早期未写入 `api_name` 的持久化
任务，避免已经验证完整的周线继续显示为 `unverified`。每日周线探测在非当周最后
交易日返回零行时，使用 `trade_cal` 证明为条件跳过；当周最后交易日的零行仍失败关闭。

## 受控父子批次

`POST /api/v1/collection-batches/fanout` 只接受服务端注册的接口和范围字段。规划器：

- 只从 `stock_basic`、`index_basic` 或白名单 `tushare_norm_*` 标准表中已允许的依赖接口
  读取证券清单，不接受调用方提供 SQL、表名或任意代码数组；
- 强制股票筹码、基金净值、指数权重等接口携带有限日期窗口，财务和股东类接口
  携带合法季度末报告期；
- 单次最多生成 200 个子任务，并返回 `next_offset` 和 `has_more`，由运维显式
  决定是否继续下一批；
- 在父任务证据中固化依赖清单总量、完整清单摘要、所选片段摘要和游标；每个
  子任务自身继续保存实际代码参数，因此之后可以证明当时究竟按哪份清单执行；
- 对转债接口在官方支持范围内合并多个代码，减少请求次数；其余接口一标的一任务，
  失败互不影响；
- 对请求计划和每个子任务生成确定性幂等键。

父任务和全部子任务在一个数据库事务中创建。父任务 `job_kind=batch` 永不被
Worker 领取；数据库触发器在每次子任务变化后汇总数量、行数和最终完成状态。
父任务只有在所有子任务均成功且不处于 `verifying` 时才可能完成，任意最终失败
都会保守标记为 `failed/incomplete`。即使当前子任务全部成功，只要计划中
`has_more=true`，或批次不是从 offset 0 覆盖到宇宙末尾，父任务仍为
`success/incomplete`，不会用局部分片冒充全量完成。控制台可查看批次明细并只重试失败子任务。

## 跨分页全量活动

单个父子批次始终有界；跨批次的全量推进由
`sys_collection_fanout_campaign` 和 `sys_collection_fanout_campaign_batch`
持久化，而不是依赖进程内循环：

- `POST /api/v1/collection-fanout-campaigns` 创建活动，Scheduler 每 20 秒协调一次；
- 首个分页把完整有序实体清单写入
  `sys_collection_fanout_campaign_entity`，并冻结来源、总数和摘要；后续页面只从
  该快照读取，实时清单变化留给下一周期；
- `next_offset` 表示已规划游标，`completed_offset` 只表示已严格验证游标，进程在
  两者之间崩溃也不会丢失或越过未验证分页；
- 只有上一页全部叶子任务为 `success`、结果为 `complete/empty` 且证据
  `verified=true` 时，才创建下一页；
- 失败、缺证据或快照损坏进入 `attention/incomplete`。继续操作只重排失败
  叶子任务并复用原父批次，不改写审计历史；
- 最后一页验证通过且 `has_more=false` 后，活动才成为 `success/complete`；全程
  确实无数据则成为 `success/empty`。
- 分区策略升级后，旧失败活动不会被伪造为成功或删除。只有同接口、同周期的替代
  活动达到 `success/complete|empty` 后，旧活动才能标记为 `superseded`，并保存
  `superseded_by_campaign_id` 与处置说明，既消除错误的待办状态，也保留原失败证据。

控制台的接口总览优先显示活动聚合状态，而非最后一个局部分页；活动明细仍可逐层
下钻到父批次和叶子任务。`full` 初始化增加独立 `fanout_baseline` 阶段，活动步骤
随初始化暂停门控，并在完整活动成功后才允许进入最终覆盖验收。该阶段现在包含 18 类
基线活动；需要日期、报告期或实体代码的接口由初始化器生成受限参数，并冻结基金、
股票、转债和指数依赖宇宙，避免用无参数探测代替真实首采。

周期配方由 [service/fanout_scheduling.py](../../service/fanout_scheduling.py)
显式维护，可通过 `GET /api/v1/collection-fanout-schedules` 查询。每日活动包含
股票因子、东财资金流、ETF 成分、TDX 成分、期权/期货交易所分区等已验证配方；
它们在独立 `worker-fanout` 中运行，不占用核心行情任务执行槽。活动叶子任务按
`daily > weekly > monthly > backfill` 设置队列优先级。

## 完整性规则

- 支持 `limit`/`offset` 的接口逐页拉取，并在
  `sys_tushare_collection_checkpoint` 保存下一页、累计页数、行数和页面哈希。
- 某些官方参数表未列出传输层分页字段，但网关实测支持标准分页。此类接口必须
  进入显式策略白名单后才能分页；例如 `fund_share` 在单个 `trade_date` 上连续
  两页均返回 2000 行，现会持续翻页到不足一页。2026-06-30 分区已用 26 页、
  25,998 行的耗尽证据验证，不能通过关闭整数上限保护来绕过。
- `index_weekly` / `index_monthly` 同样使用市场级 `trade_date` 分区和标准
  `limit/offset`。专项采集器逐页 UPSERT，并仅在短页证明耗尽后成功；重复页和
  `max_pages` 都会失败关闭。2026-08-28 周线以 15 页、14,312 行验证，
  2026-08-31 月线以 10 页、9,364 行验证，避免约八千指数代码逐一扇出。
- 进程异常退出后从失败或部分完成的 checkpoint 继续；原始表主键保证重拉
  同一页不会生成重复记录。
- 原始记录的请求身份排除 `limit` 和 `offset`，换页大小、翻页或断点续跑不会
  改变同一业务请求的哈希身份。
- 通用任务创建时把机器契约中的完整输出字段列表固化到 `fields`；不依赖 SDK
  的“默认显示字段”，避免行数完整但业务字段被静默省略。手工指定字段必须是
  契约字段的子集。
- 原始层提交后立即执行契约类型转换；通用任务只有在标准化行数与原始行数一致、
  且没有未隔离失败时才可能完成。字段缺失、类型错误和契约漂移均留下持久化证据。
- 相同 `api_name + 业务参数` 的分页任务持有 PostgreSQL advisory lock；第二个
  Worker 不会并发改写 checkpoint，而是返回可重试的范围繁忙错误。
- 日期、月份和报告期接口必须传入单日、单月或单报告期分区；无边界请求会被拒绝。
- 返回行数触及官方公布的单次上限时，任务标记为不完整并失败，不把截断结果
  当作成功。
- 分页返回任意已出现过的页面时立即停止，连 A/B/A 形式的循环也不会漏过。
- 单次分页最多 100 页；超过上限保留 checkpoint 并要求人工缩小查询范围。
- 股票日线截面在 1990–1992 年只有个位数到数十只证券，固定百分比会把正常停牌或
  未成交误报成缺失。该区间使用 `daily` 与 `daily_basic` 两个独立上游接口的同日
  截面作为交叉基线，并对不超过 20 只的微型市场容许 1 只正常未成交；1993 年起
  恢复 `stock_basic` 点时上市宇宙比例检查。指数基础表中
  缺少上市日期的记录不会反向假定为“自 1990 年已存在”，避免污染早期历史验收。
  初始化仍会保存 1990–1992 的全部单日响应，并要求请求范围有界且未命中上限；
  对全部已闭合历史分区，逐日任务以传输完整性作为硬门槛；最终覆盖阶段再对最近
  120 天执行严格上市宇宙截面验收。这样不会把上游早期“有基本面、无当日行情”的
  语义差异伪装成采集器故障，同时当前交易所分批发布仍会被严格拦截。

## 失败与恢复

- 参数错误、权限不足等永久错误不做盲目重试。
- 临时网络错误默认按 60、300、900 秒指数退避。任一任务确认 DNS 或传输故障后，
  会在同一事务中推迟同 `resource_class` 的全部待执行叶子任务，避免共享网络事故
  让历史批次在几十秒内连续耗尽重试。退避基数和上限分别由
  `JOB_NETWORK_RETRY_BASE_SECONDS`、`JOB_NETWORK_RETRY_MAX_SECONDS` 控制。
- 初始化因最终失败进入 `attention` 后，Scheduler 只会自动恢复“当前阶段所有失败
  步骤均有 `retryable=true` 且分类为 `network`、`timeout` 或 `quota`”的情况；
  完整性、权限、参数、处理器版本和覆盖审计错误继续失败关闭。自动恢复次数独立于
  人工 `verification_round` 持久化计数，默认冷却 300 秒、最多 3 轮。
- 上游限频错误按错误信息中的周期延迟重试；分钟/小时频率按请求间隔退避，
  `N次/天` 被识别为硬日配额并延迟到下一上海自然日 00:05。首个叶子任务确认
  日配额耗尽后，同接口尚未运行的兄弟任务会在同一事务中整体延期，避免数百个
  子任务连续消耗重试次数。`hk_daily` 通过数据库全局接口时间槽每天只提交一个
  有界日期请求；`stk_mins` 仍不进入常规自动队列。
- 通用和专项采集器都通过 `sys_tushare_rate_limit` 预留 Token 全局时间槽与
  接口时间槽；Scheduler、Worker 或手工进程共享 Token 时也不会互相绕过。
- 持久化任务遇到超过 5 秒的未来接口时间槽时不会在 Worker 内睡眠等待：任务会
  释放租约、保持尝试次数不变并把 `available_at` 推迟到时间槽成熟后。这样一小时
  级接口限频既不会耗尽重试次数，也不会占住日常任务执行槽或触发执行超时。
- 覆盖规则中的日期列和实体列由 PostgreSQL 集成契约逐项对照真实业务表；列名漂移
  会在 CI 阶段失败。覆盖审计的失败计数只包含尚未被更新且覆盖范围相同或更大的
  成功审计解决的故障，历史失败仍保留在任务明细中，但不会继续冒充当前故障。
- Worker 单任务默认 1,800 秒超时，防止 SDK 或网络连接永久占住资源池执行槽；
  可通过 `JOB_EXECUTION_TIMEOUT_SECONDS` 调整。
- 队列按 `resource_class` 分成日常、周期扇出、初始化/回填三个互斥 Worker 池。
  高优先级只负责池内排序；长回填即使已经开始执行，也不能占用日常任务执行槽。
- 三个 Worker 池仍通过 PostgreSQL `sys_tushare_rate_limit` 共享同一个 Token
  请求预算；隔离执行槽不会绕过全局和接口级限流。
- `factor_value` 每日全量按 `factor_name` 扇出，而不是按约 5890 只股票扇出：
  因子清单来自已标准化的历史观测，一次因子请求覆盖当日全部股票，当前约 202
  个请求即可完成，低于 1000 次/日的接口配额。全新数据库没有因子清单时，系统
  先创建一条可审计、可重试的单股票发现任务，规范化成功后再冻结因子宇宙。
- 周期扇出以“接口、数据周期、预期日期、规范化请求、采集计划版本”作为跨
  `backfill` / `daily` / `weekly` / `monthly` 的逻辑范围。创建批次前在 PostgreSQL
  事务内获取范围级 advisory lock，并复用同范围内仍在运行或已经成功的活动，避免
  调度巡航与人工修复为同一分区各建一套叶子任务。计划版本升级仍可显式创建新活动，
  以便修复旧的错误分区策略。
- Worker 重启会恢复遗留的 `running` 任务。调度器每天 07:15、09:15、13:15、19:15、
  23:15 做幂等巡航；盘后两次巡航直接提交当天交易日，避免日数据延迟到次日。
- `ccass_hold`、`etf_share_size`、`margin`、`margin_detail` 按官方发布时间视为次日 09:15
  才成熟：07:15 巡航不会提前消耗空结果重检次数，09:15 会立即补采；覆盖审计
  延后到 09:30，并在接口成熟前排除最新分区，避免把发布延迟误判成数据缺口。
  调度器启动时的预发布审计和 09:30 发布后审计使用两个稳定幂等阶段键，既不会因
  午夜重启吞掉发布后审计，也不会因同一阶段反复重启产生无界重复扫描。
- 核心 `daily` 与 `bak_basic` 还会在 16:00、19:00、23:00 对当天分区执行
  三次幂等采集，覆盖上游盘后发布时间波动和首轮空结果。
- 盘前 `stk_limit` 在 09:00 首采，并于 10:00、12:00 同日幂等重采。专项采集器
  明确返回 0 行时任务记录为 `empty`，不立即强制成熟当天覆盖审计或生成无意义的
  紧邻修复；后续计划窗口负责区分发布延迟与真正空分区。
- 专项 cron 首次发现、旧引导游标没有关联任务或运行期发生停机时，会在配置的

  交易日，`period_key`、`expected_for` 和实际请求日期保持一致；节假日由

  市场级分页修复任务，不再回退到高基数逐代码扇出。

  任务按最近一次运行判断当前健康状态，网络抖动导致的失败 attempt 若已被持久化
  重试恢复，不会在后续六小时持续误报。若历史任务缺少后续任务关联，但失败之后
  已有覆盖该日期的严格 `complete` 数据集审计，也会从当前问题中消除；原失败记录
  仍保留供审计追踪。
- 所有专项 cron 也先进入 `sys_collection_job`，Scheduler 不再直接执行上游采集。
- Scheduler、三个 Worker 池、Auditor 每 15 秒写入数据库心跳；心跳同时记录池
  接受的资源类别，状态接口汇总每个池的排队、运行和最近失败数量；容器健康检查会拒绝只剩
  数据库连接、但业务循环已经卡死的假健康状态。
- `/api/v1/collection-overview` 及控制台底部状态现在分别统计“历史补采”和“日常
  扇出”的活动数、排队数与运行数。判断初始化是否结束时只看历史工作负载，不再因
  当天自动生成的例行采集活动而误判为“历史采集仍在持续”。

  把全部历史指数作为任一交易日的活跃截面会制造稳定的假 `partial` 告警。只有在

[历史完整性、采集时效与告警真实性审计](../../reports/history_and_timeliness_audit_2026-09-06.md)。

交易日历基础任务已改为按年份和交易所分区，真实任务一次写入 26,626 行并覆盖
SSE 1990-12-19、SZSE 1991-07-03 起的日历，避免超长单请求被静默截断。全历史
初始化可以据此生成核心日频任务，但不会在普通升级或审计时未经确认自动启动。

本轮还发现两融接口存在“请求完整但上游当日截面不完整”：2026-09-04 的
`margin` 只有 1/3 个交易所，`margin_detail` 在 offset 两页后穷尽于 2,000 行。
系统现在同时保留分页耗尽证据和截面覆盖失败，物理表已有行也不会遮蔽
`partial`。这不是本地截断，也不能被标成严格成功。

两融明细的截面基准已改为同日 `margin_secs` 两融标的池，而不是全部上市证券。
2026-09-04 的标的池为 4,468 个、明细仅 2,000 个（44.76%）；此前完整日期均约
99.4%，因此使用 98% 阈值既允许极少量合法差异，又能准确识别交易所分批发布。
覆盖修复使用“数据集 + 分区 + 业务日”幂等键：同一天不会重复轰击上游，缺口跨日
仍存在时会由下一次审计自动重采，补齐后再审计闭环。

全历史初始化还暴露了 `stock_limit` 起点定义错误：涨跌停规则的制度起点不等于
Tushare `stk_limit` 接口的数据起点。真实 Token 逐年、逐日探测确认 1996–2006
均返回空，首个稳定可取得分区为 2007-01-04。初始化现只从该日开始要求非空，
2007 年后的空结果仍保留严格完整性保护；此前 118 个早期空响应不再被误判为失败。

覆盖总览的“最新审计”按被审计区间的 `end_date` 优先，其次才按执行时间排序。
这样历史单日修复审计不会覆盖最近 120 天的全局审计结论。统一状态入口
`GET /api/v1/data-health` 同时聚合采集任务、覆盖、时效和初始化，但保持四类证据
彼此独立：真实缺失/截面不完整、空数据集、尚未首采、尚未证明完整。控制台对前两类
使用“已确认”，对后两类使用“完整性未知”，不会用一个含糊的红色失败数混在一起。

事件型数据使用显式 `event_driven` 时效策略：没有新事件不等于采集陈旧。覆盖审计
告警只针对 `scheduled=true` 的规则；可按需审计但没有可靠预期日历的数据仍出现在
分类总数中，不作为运行故障。接口与其数据集别名共享根因键，避免一次失败同时显示为
“接口失败”“数据集为空”“覆盖缺口”三条独立问题。

控制台进一步将“真实异常”“待验证”“已验证空结果”拆分。近 6/24 小时失败指标
只统计同分区尚无后续成功的执行失败；若执行已恢复但覆盖仍不完整，只显示覆盖异常，
避免旧失败重复告警。专项 cron 返回零行可能表示真空或非交易日跳过，因此保守标为
`unverified`；只有带穷尽证据的任务才标为已验证空结果。专项 cron 的持久化队列任务
保存规范化接口身份；对已有规则的数据集，写入后自动进入关联覆盖审计，控制台优先
展示这条可重试、可审计的队列证据，而不是旧的行数型运行日志。
当日任务的 `unverified` 会按持久化任务 ID 与交付计划精确关联：截止时间之前展示为
“等待复采”，截止后仍无完整性证据才升级。只按接口名匹配不足以隐藏旧任务，因此
未来计划不会替过去的未验证任务消警。

初始化的大阶段按最多 500 个任务滚动物化。数据库中的 `planned_steps` 只代表已经
生成的任务数，不能作为阶段总量。初始化 API 现在额外返回稳定的
`logical_total_steps`、`materialized_steps`、`remaining_steps` 和基于逻辑总量计算的
`progress_ratio`；控制台分别展示“已完成 / 逻辑总量”和“已生成”，避免每个滚动
批次都错误显示为接近 100%。该比例仍仅代表当前阶段，不代表七阶段全流程进度。
本次变更持续通过完整单元与真实 PostgreSQL 集成测试；活动初始化占用全局
单例，因此另 1 个“新建初始化”活动用例按设计跳过。

重新执行历史初始化前，应先调用
`POST /api/v1/initialization/preflight`。预检不会创建任务，会一次性验证任务注册、
接口可采契约、全量扇出配方、严格覆盖规则和专项采集器白名单，并返回稳定的
`plan_version` 与 `plan_fingerprint`；初始化活动也会持久化这两个值。这样部署缺件
会在开始前阻断，而不是运行数小时后才暴露。最新基线若截止日在周末，会统一使用
最近交易日；已经由财务历史阶段穷尽的披露计划、快报、预告和主营构成不会再由
专项基线重复执行。

## 每接口、每周期完成判定

策略调度为每个接口、每个周期创建独立的 `sys_collection_job` 记录，保存
`api_name`、`cadence`、`period_key` 和 `expected_for`。运行结束还会保存
`rows_fetched`、`rows_inserted`、`completion_status` 与 JSONB
`completion_evidence`，因此可区分以下状态：

- `complete`：有界分区或分页耗尽已得到证明，并且上游返回了数据。
- `verifying`：规范化写入成功，关联的日期/报告期与截面审计正在排队或运行。
- `empty`：完整请求执行成功但上游返回 0 行；它不会冒充完成，需要确认数据
  发布时间或该周期本就没有事件。
- `incomplete`：触及官方上限、可疑整数上限、分页重复或最大页数，明确判为不完整。
- `unverified`：任务成功写入但旧采集器还没有提供完整性证据。
- `pending` / `running` / `retrying` / `failed`：排队、运行、等待重试和最终失败。

## 通用采集器与专项采集器的边界

| 维度 | 通用采集器 | 专项采集器 |
|---|---|---|
| 目标 | 快速、安全覆盖授权只读接口 | 提供稳定业务模型和高效查询 |
| 落点 | 原始审计层 + 每接口独立 `tushare_norm_*` 强类型标准表 | 声明字段和主键的领域业务表 |
| 完成证明 | 有界分区、分页耗尽、页哈希和 checkpoint | 与通用路径共享有界分区/返回上限检查；有覆盖规则时继续验证日期及截面 |
| 扩展方式 | 增加/修正机器可读接口契约、表迁移与策略 | 显式采集类、表结构、调度和覆盖规则 |
| 自动路由 | 仅 `generic_raw` 契约；固定到契约标准化处理器 | 根据 API 解析唯一专项类，并固化处理器快照 |

所有自动调用先生成 `sys_collection_job`。任务创建时保存 handler 类型、逻辑 key、
版本与代码 revision；运行前再次解析并比对，避免部署后旧任务被静默路由到另一种
实现。周期任务的幂等键同时包含处理器类型、逻辑 key 和版本的指纹；处理器升级会
创建一次新的迁移重采，同一处理器版本的重复派发仍被严格去重。策略路由到专项采集器时，必须先通过与通用采集器相同的参数分区和可疑上限
验证，证据会直接写入 `completion_evidence`。专项任务成功后，支持覆盖规则的任务会在同一事务中创建
`sys_data_coverage_job(collection_job_id)` 并进入 `verifying`。Auditor 反写最终
状态，必要时通过白名单映射生成限量、幂等补采；没有可靠规则的任务保持
`unverified`，系统不会用“返回行数大于零”冒充完整。初始化中声明
`require_verified` 的步骤还会检查机器可读证据，旧任务即使状态字符串为
`complete` 也不能绕过验收。Auditor 自身重试也按
coverage job 幂等更新同一审计证据，不会制造重复审计记录。

通用标准表的 `_record_hash` 是完整 payload 技术主键，因此同一业务对象在上游字段
变化后会保留多个版本。经过输出契约复核的业务身份通过 `tushare_current_*` 只读
视图选取最新版本；任何身份字段为空的记录都不会被折叠。REST 数据集会公开
`storage_semantics`、`business_identity_fields`、`identity_confidence` 和
`read_view`，调用方无需猜测表语义。启发式身份不创建当前视图或唯一约束。

标准化运行、隔离错误和字段漂移分别记录在 `sys_tushare_normalization_run`、
`sys_tushare_normalization_error`、`sys_tushare_schema_drift`。健康总览可通过
`GET /api/v1/normalization` 查询；未解决的警告级漂移或隔离错误会使对应接口状态
降级，信息级上游技术字段只保留审计证据，不制造误告警。

PostgreSQL 的 `text` 和 `jsonb` 不能表示 NUL 字符。通用与专项采集统一在存储边界
递归清除上游字符串中的 `\\x00`，不会丢弃整行；任务证据的
`sanitization.nul_characters_removed` 和 `affected_fields` 记录清洗数量与字段。
`dc_concept_cons` 的历史故障样本已验证为 `reason` 字段清除 1 个 NUL 后完整入库。

采集控制台位于 `http://127.0.0.1:8000/dashboard`，按运行总览、接口任务、扇出活动
和覆盖审计分区展示；可以按接口、周期、状态和编排方式筛选，查看获取/新增行数、
判定原因，重试失败任务，或幂等生成最近
日、周、月、季度的补采清单；父子批次会显示成功、失败和待处理子任务数量，
全量扇出活动会显示已验证实体/分页进度并支持暂停、继续和逐层下钻。所有主列表及
弹窗明细都限制单页行数，筛选会重置页码，避免长历史任务一次性渲染。状态 API 为
`GET /api/v1/collection-overview`。

覆盖审计页支持按数据集和起止日期查询 `missing` / `partial` 明细。指定范围补采采用
“先审计、后修复”的证据链：`POST /api/v1/coverage/audits` 只读检查本地业务表，
`POST /api/v1/coverage/repairs` 只对持久化审计已确认且存在安全参数映射的分区生成
幂等任务，不把未审计日期、非交易日或观察型数据误判为缺失。初始化总览同时返回
当前阶段已物化范围和 queued/running 工作范围，避免用总目标区间冒充正在采集区间。
