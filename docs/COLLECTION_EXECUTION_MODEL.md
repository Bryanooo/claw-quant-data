# V2 采集执行模型

自 2026-09-29 起，Tushare 只由 V2 编排。V1 的队列、扇出活动、初始化记录和运行服务不再参与执行或展示。

## 任务边界

一个 `task_execution` 对应一个可独立验收的逻辑数据周期：交易日、自然周、自然月、报告期或快照。HTTP 分页、日期窗口收缩、证券/市场枚举都在 `acquire` 节点内完成，不拆成调度层“叶任务”。

每个采集任务固定包含五个节点：

1. `condition`：判断交易日、发布时间和运行条件；
2. `scope_plan`：冻结日期、业务分区、请求参数及幂等身份；
3. `acquire`：穷尽分页和分区，幂等落库并保存请求级证据；
4. `validate`：由独立审计代码检查业务表、实体覆盖和传输完整性；
5. `publish`：只有验证通过才发布 `dataset_state.ready=true`。

任务成功与数据就绪是两个不同事实。采集请求完成但验证发现缺口时，执行进入 `attention`，数据状态保持 `gaps` 或 `partial`。

## 三类运行

| 用途 | 触发 | 资源池 | 范围 |
|---|---|---|---|
| 日常采集 | Scheduler | `v2-routine` | 当前应发布周期 |
| 初始化 | 安装/API | `v2-backfill` | 全历史审计确认的缺口 |
| 修复/补采 | 审计/人工 | `v2-backfill` | 一个已确认缺失或不完整周期 |

初始化不维护第二套采集器。流程是：严格审计 → 生成 V2 repair 实例 → 同一任务采集与验证 → 再审计。历史资源池在 SSE 交易日 08:30–16:00 不领取新实例，已开始的实例不会被强制中断。

## 控制面

V2 只使用 `orchestration_v2` schema 的五张表：

- `acquisition_endpoint`：数据源接口契约和凭据引用；
- `task_definition`：任务定义及所有历史版本；
- `task_execution`：实例、节点状态、租约、重试和最终错误；
- `task_execution_event`：追加式执行与验证证据；
- `dataset_state`：经过验证的数据事实状态。

凭据引用形如 `env:TUSHARE_TOKEN`。数据库中的任务定义不能保存或动态执行 Python 代码；handler 必须来自代码白名单。

## 重试与纠错

- 网络、超时和配额错误按分类退避；永久参数/权限错误失败关闭；
- Worker 使用租约和心跳，进程退出后可回收实例；
- acquire 节点保存请求完成证据，重试跳过已经验证完成的请求；
- 错误契约产生的终态实例使用 `superseded` 保留历史，再以新定义创建替代实例；
- 不删除失败证据，不把权威空结果和“没有执行”混为一谈。

## 调度与依赖

Scheduler 只创建实例，不直接调用上游。下游应依赖 `dataset.ready` 事件，而不是采集函数返回或执行状态。日、周、月、季度的业务日期均写入 `observation_*` 字段；创建日期仅用于运维排序。

运行状态通过 `/api/v1/ops/orchestration-v2/*` 和 Dashboard 查看。
